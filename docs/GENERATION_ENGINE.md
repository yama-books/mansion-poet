# ポエム生成エンジン設計

更新日：2026-10-17  
状態：**設計仕様。v0.1.1のテンプレート生成は現存し、以下の大半は未実装。**  
関連：[開発マスタープラン](DEVELOPMENT_PLAN.md)／[施設・自然地物の採用と配慮ポリシー](POEM_SUBJECT_POLICY.md)

## 1. 狙う表現

モデル文章例（創作。実際の地域の評価ではない）：

**地名**：神保町  
**素材**：周辺で検出された書店、図書館、文化的な施設の存在  
**主題**：知の蓄積と新しい暮らしの交差  
**Heritage / 濃度90の例**：

> 知の深奥に、邸の答えを。  
> 文字と街路が織り成す、幾重もの都市の記憶。  
> いま、日常という名の新しい叡智が、この地に刻まれる。  
> THE JIMBOCHO RESIDENCE

※書店・図書館などは**実APIで取得・採用できた場合のみ**固有名詞や特徴に使用。未確認なら「書物が息づく街」なども事実の断定になり得るため避ける。

### 表現上の目標

- その土地のために書かれたように感じる。
- 広告らしい格調と形式がある。
- 根拠となる情報と、創作上の修辞が自然につながる。
- 書式・語彙・主題の繰り返しが気にならない。
- 濃度を変えると語彙だけでなく、文の長さと抽象度が変わる。

## 2. データパイプライン

入力：
\`\`\`ts
type Location = {
  displayName: string;
  lat: number;
  lon: number;
  selectedAt: number;
  selectionId: number;
};
type Evidence = {
  id: string; source: 'OpenPOI' | 'OSM' | 'GSI';
  name: string; lat?: number; lon?: number;
  distanceMeters?: number;
  category: string; themeTags: string[];
  address?: string; license: string[]; attribution: string[];
  confidence: 'high' | 'medium' | 'low';
  validationFlags: string[];
};
type ThemePlan = {
  primary: string; secondary?: string;
  anchors: string[]; prohibitedClaims: string[];
  evidenceIds: string[];
};
type Poem = {
  propertyName: string; headline: string;
  body: string; disclaimer: string;
  evidenceIds: string[]; seed: string;
  version: string;
};
\`\`\`

上記はモデル例。JavaScript実装時は型をJSDocで持たせてもよい。ブラウザ互換のビルドなし構成を優先。

### 処理の責任分離

- \`fetch\`：APIからそのまま取得。
- \`normalize\`：返却形式の変換、文字種・座標・ライセンス、スキーマ検証。
- \`validate\`：距離、住所矛盾、明らかな誤分類、名称重複。
- \`interpret\`：土地特徴スコア、主題選定。出典なしの主題を生成しない。
- \`compose\`：見出し・本文・物件名の生成。API呼出しなし。
- \`render\`：DOM表示。ユーザー入力や外部文字列はtextContent等で扱い、HTMLとして解釈させない。

## 3. Evidenceの妥当性

### 採用の分類

**A: 主題に使える**  
カテゴリー・名称・座標・住所に重大な矛盾がなく、地域と対応。例：周辺の図書館がPOIとして得られた場合の「文教・知性」主題。

**B: 画面に参考として表示するが主題にはしない**  
名前からしか分類できないものや、名称とカテゴリが矛盾する施設。例：「お酒の美術館」のような店舗、ショッピングモール中の店舗、閉業疑い、住所矛盾。

**C: 採用しない**  
距離外、緯度経度の不正、重複、名称無し、ソースに含まれない固有施設名、位置やカテゴリの重大な矛盾。

※Aでも「現在営業している」「眺望がある」「学区が優秀」といった事実を保証しない。

### 重複解消

- 正規化名称（NFKC・余白・記号、ただし意味のある法人名を無闇に削らない）。
- 同座標付近／同名の候補は統合。名前が同じだけでは別店舗の可能性があるため、距離条件を必須にする。
- 信頼度が高いソースを使い、licenseとattributionは**失わず合併**する。
- ユーザーの選択地点からの距離は必ずアプリ側で計算する。

### 施設数・偏り

- 周辺に店が多くても、「食」一辺倒で街を表さない。
- 同じテーマの独立施設数は頭打ちにする。
- 高密度地域では無条件近傍クエリが店で埋まることがあるため、カテゴリ・特徴語などを複数回に分けて補完する方針を検証する。
- 大量リクエストは避ける。最初は現行の無条件＋特徴語検索を基準とし、利用回数・必要性・API制約を見ながら変更。
- OpenPOIの\`q\`複数語検索はOR、\`center\`指定時は距離順、\`limit\`は最大200。検索結果が全施設の網羅リストでない点に注意。

## 4. ThemePlanの判定

初期候補テーマ：
- \`knowledge\`：知性・文教
- \`history\`：歴史・継承
- \`culture\`：文化・芸術
- \`green\`：自然・公園
- \`water\`：水辺
- \`transport\`：都市・交通
- \`commerce\`：街の賑わい・商業
- \`daily\`：日常・暮らし

重み付けは素案。チューニング前は**検証済みの数値として扱わない**。

\`\`\`text
score(theme) =
  Σ over evidence {
    confidenceWeight
    × distanceWeight
    × themeMatchWeight
    × duplicatePenalty
  }
  × diversityBonus
  × saturationCorrection
\`\`\`

- 距離は直線距離の連続減衰（例：exp(-distance / scale)）。
- 高密度エリアのPOI数は平方根またはlog圧縮。
- 主題候補の上位3つを保持し、作品ごとに主題を変えられるようにする。
- 主題が弱いときは「この地点の特定施設が特徴」と決めつけない。
- \`style\`は取得済みの生証拠を変えず、主題の優先順位と文章設計だけを変える。
- 結果に「主題にした根拠」リンクを付ける。

## 5. 文章の生成

### 語彙辞書

\`\`\`json
{
  "knowledge": {
    "nouns": ["知", "叡智", "思索"],
    "phrases": ["学びの気配", "知の層"],
    "avoid": ["名門", "日本最高峰"]
  },
  "history": {
    "nouns": ["記憶", "時の重なり", "継承"],
    "phrases": ["時を重ねる街"],
    "avoid": ["由緒正しい", "千年の歴史"]
  },
  "green": {
    "nouns": ["緑", "余白", "季節"],
    "phrases": ["緑の余白", "季節の気配"],
    "avoid": ["森の中", "一望"]
  }
}
\`\`\`

「使える表現」も、文脈次第で事実を主張する。すべての単語が自動的に使用可能ではない。綴り・仮名・同義語・長い語の扱いを検査する。

### 文の骨格

\`\`\`text
PropertyName:
    [THE] [日本語地名の表記あるいは確認済みの英語表記] [RESIDENCE / COURT / MAISON]

Headline:
    強い一行の象徴（地名 or 主題を直接書く案）
    + 二行目に逆説／到達／余韻（必要な場合）

Body:
    1. 地名あるいは実在が確認できた施設（事実に近い記述）
    2. それを抽象化する表現（創作）
    3. 日常・住まいの哲学（創作）
    4. 過度に格調高い余韻（創作）

Evidence:
    具体的に参照した項目／出典・距離・状態
\`\`\`

文を文章片だけで連結すると助詞・語尾が破綻する。各テンプレートに「名詞句」「場所句」「述語」「末尾句」などのスロット型を定義し、品詞・助詞を合わせる。まずは少数の良質な完結文テンプレートで構文単位を管理。

### 生成方式

**v0.2**：現行テンプレートに5案程度の構文増と禁止語検査を導入。  
**v0.3**：ThemePlanで主題を変える。  
**v0.4**：文の骨格、句の選定、物件名を独立生成。  
**将来**：任意のLLMにThemePlanを渡すが、事実を確認する後処理を必須にする。LLMへのAPIキーは静的公開ページに直書きしない。

### 再生成

- \`seed = hash(location + style + intensityBand + generationIndex + generatorVersion)\`。
- 同じseedで同じ文章に復元できる（共有・回帰テスト向け）。
- 連続した5案では、前回の主題・見出し構文・末尾句をなるべく使わない。
- 施設が再取得されて変化したら\`dataVersion\`や\`retrievedAt\`を記録。永久に同一を保証するのは文章辞書とEvidenceのスナップショットがある場合のみ。
- キャッシュは**取得データ**に対して適用し、テーマ別の整列済みリストを文体をまたいで誤使用しない。

## 6. 濃度による差

| バンド | 狙い | 文章のイメージ |
| --- | --- | --- |
| 0–20 | 控えめ | 「神保町という街で、新しい暮らしを。」 |
| 21–40 | 上品 | 「街の文化にふれながら、豊かな日々を。」 |
| 41–60 | 王道マンション広告 | 「都市の時間を、私邸の流儀へ。」 |
| 61–80 | 壮大 | 「都市の深奥に、新たな邸宅思想を。」 |
| 81–100 | 極端な詩的表現 | 「この座標こそ、邸宅の最終到達点。」 |

この例文はテンプレート候補。特定の文化的な街という断定はEvidenceがある場合だけ許可。

### 濃度と真実性を混ぜない

誇張対象は**レトリック**のみ。施設名やアクセス・景観を嘘に変えない。濃度100でも「ここは誰も知らない最高級住宅地」等の検証不能な広告上の優良誤認は書かない。

## 7. 日本語品質基準

- 助詞の不自然な連続を避ける：「のの」「へへ」「をを」など。
- 抽象名詞の連続を過剰にしない。「時の記憶の永遠の…」など。
- 反復出現する「その」「選ばれし」「至高」「悠久」を辞書で制限する。
- 文章末尾をすべて「ここにある」で閉じない。
- 地名・長音・全角記号・カナ・漢字が混在した場合に破綻しない。
- 「地図で選択した地点」「THE LOCATION」など仮名がそのまま物件名に出ないようフォールバック。
- 英語名のローマ字化が難しいときは元の地名のまま、または無難な英語の架空物件名を用いる。誤ったローマ字を捏造しない。
- 長い地名に対する見出し長・折返し・句読点を制御する。

## 8. レビューと評価指標

### 人手評価（5段階）

1. **土地への適合**：その場所ならではの主題か。
2. **マンション広告らしさ**：品位・大げささ・広告的な語りがあるか。
3. **日本語の自然さ**：不自然な接続や繰り返しが少ないか。
4. **変化の豊かさ**：別案を作る意味があるか。
5. **事実の節度**：未確認の景観・歴史・高級感を事実と誤解させないか。

採点基準：1=不十分、3=実用的、5=非常に良い。新旧版で代表地点・seedを揃えたブラインド比較も行う。目標は各平均4/5以上、事実の節度に重大違反なし。少人数レビューでは数値を絶対視しない。

### 自動テスト

- 文型・辞書の参照漏れがない
- 1案は空でない／変数未置換がない
- 同seedは同結果
- Evidenceにない固有名詞を持ち込まない
- 長い地名でもDOM表示が切れない（ブラウザテスト）
- 無根拠の「徒歩」「眺望」「必ず」「資産価値」「名門」等はルールベースで警告し人手で判定
- 異なるseed5本で少なくとも3種類の見出しテンプレートを使用
- 同じ文体・濃度で再生成しても文意が破綻しない

### 評価地点

代表データは [QUALITY_TEST_PLAN.md](QUALITY_TEST_PLAN.md) を参照。特定の施設・文化財の存在は、テスト用取得済みfixture以外から創作しない。

## 9. 説明可能性

作品の下にコンパクトな一行を出せるようにする。

例：
\`\`\`text
主題：文教 × 文化
素材：図書館（OpenPOI）／博物館（OSM）
範囲：選択地点から直線850m以内
注記：取得情報の一部を用いた創作文です
\`\`\`

どの施設がどの言葉を生んだか、可能な限り追えるようにする。自動評価やパロディの面白さより、未確認の具体的事実を出さないことを優先。
