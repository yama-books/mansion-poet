## 1. 原則

**画像を先に100枚作ってから仕組みに合うか悩むのではなく、実際の広告にきれいに掲載できた成功パターンを1つ確認してから、自由度を損なわない範囲で増やす。**

REF（文字入りの完成広告見本）とART（広告に差し込む文字・価格・地図などが描き込まれていない独立画像）を区別する。完成広告REFは画風・構図研究に使い、すべてのREFに対応するARTを作る義務はない。ARTも画像ごとに厳密なseed、長い仕様MD、固定アスペクト比、統一ppiを試作段階で要求しない。

ユーザーが自作したオリジナル画像について都度の形式的な権利審査を繰り返さない。第三者由来の新素材を混ぜる場合は別途確認する。本番使用は掲載品質の確認に基づいて判断する。

## 2. 量産へ進むための最小条件（「ひと段落」の定義）

| 条件 | 必要な確認 | 現状 |
|---|---|---|
| **A：制作原画の保全** | 文教・緑地・都市小設備を中心とする最初の独立ART候補3点について、実画像・テーマ・GitHubの相対パスとcommitを確認できる。3点に達しなくても、納品できた内容と不足を明示する | **独立生成の高解像度ART原本3点は未確認**。PR #37の写真切り出し3点とは区別 |
| **B：本物のARTで組版** | PR #39の差し替え枠に、文字なし独立ART候補を**少なくとも1点**入れて、文字・施設・地図を別レイヤーとして保てることを、WebプレビューとA4で確認 | PR #39では既存REF切り出しで差し替え技術を確認済。新ART差し替えはこれから |
| **C：視覚レビュー** | 掲載した絵が潰れず、文字が読めること、トリミングや見出しとの相性を人が目視して確認する。「直すべき点」と「このまま拡張可能」を区別する | ユーザーによる新ARTの見た目の受入は未実施 |
| **D：記録の所在** | 元ファイルと掲載例、検証結果の所在がGitHubで追える | 既存マスター・画像案内板は作成済。新ARTは未登録 |

**A〜Dの要点が満たされれば量産フェーズへ移る。** 逆に、すべてのSafari機種検証、PRINT03の全版型完成、画像の完全再現プロンプト、100%の品種網羅を量産着手の前提にしない。Safari等の受入はWeb公開時に継続する。

## 3. 量産の構成：最初は12点、結果を見て段階的に

### Batch 1：多様性確認の12点（最初の「まとまった制作」）

テーマの偏りを防ぐため、まず**6テーマ×2点＝12点**を制作候補とする。1枚1場面・1ファイル。

| テーマ | 例 | 創作上の方向性（規格ではない） |
|---|---|---|
| KNOWLEDGE｜文教・書店 | 書棚、街の読書空間 | 暖かい光、奥行、紙の質感 |
| GREEN｜公園・並木 | 並木道、木立、緑地の遠景 | 午前の透過光、季節の違い |
| WATER｜水辺・暗渠 | 抽象水彩、水にちなむ都市の質感 | 暗渠を実際の開水面と混同させない |
| HERITAGE｜歴史・文化 | 木組み、石畳、建築のディテール | 実在史跡の直接コピーにしない |
| NIGHT｜都市夜景 | 帰路の窓明かり、都市の薄暮 | 暗部の階調、文字の載る余白 |
| SMALL｜都市小設備 | 郵便ポスト、路地、小さな境界 | 都市のささやかな主役を美しく |

各テーマの2点は、**光・視点・画風・主役のいずれかを明確に変える**。単なる配色差・同一構図の大量水増しを避ける。ユーザーの希望があれば、制作中にテーマ配分を変えてよい。

### Batch 2以降：必要なものを優先して拡張

- Batch 1のうち、広告への実装で成功した主題と不足した主題を把握する。全12点のA4厳密検査は要求しない。
- 次は**24点程度**を一つの管理単位の目安とし、構図・画風の選択肢を広げる。制作点数は固定ノルマではない。
- さらに必要なら**総数60点規模**を一つのレビュー節目とする。完成広告REFと独立ARTの数字を混ぜない。目的なく100点を先に作る必要はない。
- **大型バッチの途中でも**良い画像は先にWeb組版へ使ってよい。最初の12点の全完了まで実装を止めない。

## 4. 最小限の原画登録

**必須**は「一意のファイル名、原画像、短いテーマ、REF/ART区分、GitHubのcommitとパス」。寸法・容量・SHA256は登録時にスクリプトで計算できれば自動記録する。手書きの長い説明書・モデルseed・大量の評価数値は不要。

推奨保存場所（既存実装や運用と競合する場合は担当で調整）：

- 生成原本：`assets/art-originals/<art-id>.png` などの編集前ファイル。**原本を上書きしない**。
- 画像一覧：既存の `APP003_ASSET_WORKBOARD.md` へ**バッチのGitHub保存先のリンクだけ**追加。画像ごとの巨大な情報を管理ファイルへ写さない。
- Web/印刷用の変換版：正式採用するものだけIMG-PIPE（PR #30）とIMG-00（PR #33）の規約に沿って準備。PR #30/#33は未統合なので、途中試作の段階で新画像全件をパイプラインへ無理に通さない。
- 公開サイトへ出るものとGitHubへ保管するだけの画像を区別する。Public Repoなので、公開できない素材はここに置かない。

### 簡易manifestの候補

```json
{"id":"ART-KNOWLEDGE-001","theme":"KNOWLEDGE","role":"ART-candidate","originalPath":"assets/art-originals/ART-KNOWLEDGE-001.png","status":"saved-unreviewed"}
```

このJSONは例であって**現実のファイルが既に保存されたとの宣言ではない**。一括登録スクリプトが生成できる項目は増やしてよいが、制作担当の手作業を増やす運用にはしない。

## 5. Webアプリでの使用と更新条件

1. 最初の1点がPRINT03で差し替えられることを検証した後、画風とテーマを選べる**少数の実装サンプル**を用意する。
2. 既存の主役施設・POEM・LOCATION・地図・出典はWeb側で生成し、画像中の文字や地理情報を読み取ってデータにしない。
3. 画像なし、通信失敗、低解像度、未採用は既存SVGへ安全に戻す。新ARTの存在だけで画像スロットを勝手に有効化しない。
4. iPhone Safariは公開時の受入項目。CIのChrome/WebKitエミュレーション、公開HTTP、実機操作は別々の根拠で記録する。
5. 各バッチが保存できた節目、初めて広告に採用した節目、Pagesに公開した節目にだけ、全体マスターと画像案内板を更新する。

## 6. 同時セッション分担と停止条件

- **画像制作**：原画像と最小メタ情報を専用ブランチ/PRへ保全。PRINT03やWebトップのコードは触らない。
- **PRINT03組版**：PR #39の画像差し替え・PDF検証に集中。初期3点のうち少なくとも1点と差し替えてデザイン結果を示す。
- **Web UI**：PR #40のiPhone操作性と実機受入を進める。別担当のPRINT03ソースを直接編集しない。
- **進捗監理**：本書は量産戦略、全体マスターは工程管理、画像案内板はファイル住所録。競合する編集を避ける。

**停止・方向修正する場面**は、画像が文字・地図と一体化して実装に使えない場合、参照画像の焼き直しばかりでバリエーションが増えない場合、公開・印刷に必要な画質に達しない場合、画像の所在が追えなくなった場合。それ以外は細かいゲートを増やさず制作を続ける。

## 7. 次の一操作とCHECKPOINT

1. 初期の独立ART3点のGitHub保存コミットを確認し、PR #39の掲載例から代表1点を仮差し替え。
2. 画像・文字・地図の独立性とA4の読みやすさをレビューして、量産移行条件A〜Dに照らして「着手可能／要修正」を決定。
3. **着手可能ならBatch 1の12点へ進む**。続けて保存先と配分だけを案内板で管理する。

最初の量産バッチを制作済みと記録してはならない。実際のGitHubへの画像保存と読戻しがあった件だけ成果とする。
