# THE REALITY：住環境・生活アクセス機能仕様

更新日：2026-10-17
対象：POÈME / ESTATE
状態：**採用検討用設計案。現在の公開サイトに「住環境」機能は未実装。**
関連：[ADVERTISEMENT_RESEARCH_PLAN.md](ADVERTISEMENT_RESEARCH_PLAN.md)、[DATA_SOURCES.md](DATA_SOURCES.md)、[DEVELOPMENT_PLAN.md](DEVELOPMENT_PLAN.md)

## 1. コンセプト

**「THE DREAM（この街の夢）」と「THE REALITY（ここでの暮らし）」**。

マンションポエムの世界観を楽しんだそのままの選択地点で、そこに暮らすと何が徒歩圏・日常圏にあるのかを地図で確認できる。広告を批判するだけではなく、街の魅力や生活の具体性を発見する体験にする。

**物件ではなく「地図上で選択した地点の周辺環境」を示す**。架空のマンションが本当に建っているという意味ではない。購入判断に必要な居住可能性、建築規制、治安、学区、災害、間取り、騒音、地価等は現在のデータでは保証できない。

二層の意図：
- DREAM：地名と証拠から壮大な架空の高級住宅広告を生成。
- REALITY：買物・交通・公共施設・健康・憩いなど、実際のPOIと距離・取得状態を透明に見せる。
- 同じ選択地点と検索条件を共有。ポエムの内容を変更しても現実の施設データ自体は変えない。

## 2. 最小で価値のある画面

### 標準の導線

~~~
場所検索または地図で地点を選択
   ↓
「この街を、詩にする」
   ↓
[THE DREAM] を大きく表示（現行サイトの華やかな画面を維持）
   ↓
[THE REALITY：この場所で暮らすと？] の控えめな入口
   ↓
  生活圏の地図／近い施設／距離／データの確からしさ
   ↓
[THE DREAMへ戻る]／[施設の出典を見る]／[次の土地を選ぶ]
~~~

PC：作品が主、生活情報は隣のサマリーまたは次節へ。スマホ：同時に長い2カラムを押し込まず、結果直後のタブか折りたたみセクションを使う。地図の既存DOMを重複して初期化しない。生成画面での追加通信が主フローを遅らせないよう、住環境のリクエストは必要になったときだけ始める。

### 初版のカテゴリ

| 区分 | 施設例 | 優先度 | 注意 |
| --- | --- | --- | --- |
| 買い物 | スーパーマーケット、食料品店 | 高 | 単なるスーパー名の文字一致に依存しない |
| 日用品 | コンビニ、ドラッグストア | 高 | OpenPOIでは薬局独立カテゴリが不十分な可能性 |
| 交通 | 駅、公共交通結節点 | 高 | 駅入口・改札位置まで正確とは限らない |
| 休息 | 公園、広場、緑地 | 中 | OSMなどで補完。公園の入口・開放時間は要確認 |
| 文化 | 図書館、書店、博物館 | 中 | 「文化的な街」を体験する施設 |
| 医療 | 診療所、病院、薬局 | 中 | 休診・受診可否は別途確認 |
| 食事 | カフェ、飲食店 | 中 | データ量が多い。全店舗列挙より種類と近い3件 |
| 子育て・公共 | 保育施設、学校、行政施設 | 後続 | 学区・入所資格・利用可否は断定しない |

v0.xの初版は**買い物・日用品・交通・休息・文化**を優先。詳細な学校選択、医療施設の質、営業時間、住民属性は取り扱わない。

### 表示単位

施設カード例（架空の表示例、実在施設の存在は示唆しない）：
~~~
SUPERMARKET  食料品店
○○スーパー
直線距離 約420m
取得元：OpenPOI / 最終取得：YYYY-MM-DD
[地図上に表示]  [データ元を確認]
「営業中」「徒歩5分」は確認できないため表示しない
~~~

各カテゴリは3件程度に絞る。利用者が「さらに見る」を押したら残りの候補へ。施設ゼロは「見つかりませんでした」と表示し、「この地域には存在しません」と断定しない。取得日が古い施設には明示する。

## 3. 距離・時間の厳密な区別

**初版は、検証済みの緯度経度から計算する直線距離を基本とする。**

- 中心地点：利用者が地図で選択した地点の座標。
- 初期探索半径：850m（現行アプリの検索結果と一致させる）。
- 生活圏向け半径の候補：500m / 1,000m / 1,500m。施設密度とAPI応答数・ライセンスを検証後に導入。
- 施設表示：例「直線距離 約420m」。徒歩距離・徒歩分数と明確に区別。
- 実際の道路経路がわかる場合に限り、「徒歩経路 約○m／推定○分」など別の表示で追加。道順、歩道・河川横断、駅入口、横断待ち、段差などで実感と異なる可能性を注記。
- 距離0m付近でも実際の建物の高さ・施設入口の位置や、建物への自由な出入りを保証しない。
- 「駅まで徒歩5分」を直線距離の換算だけで生成しない。

不動産広告における徒歩表示の実務基準は**道路距離80mにつき1分（端数切り上げ）**。アプリは正規の物件広告ではないが、直線距離を80m/分で割った数を「徒歩○分」と表示しない。詳細：https://www.sfkoutori.or.jp/ippansoudanjirei/徒歩所要時間について/ （正式URLは公開時に確認）。

徒歩ルーティングの技術選択は別途調査：OpenStreetMap系の徒歩ルーティング・道路ネットワークデータ等。OSRM公開デモのような無保証・利用規約のある公開サーバーを本番の無制限無料APIとして想定しない。ルートAPIのCORS、ライセンス、安定性、利用量、歩行者経路精度を比較してから採用する。

## 4. OpenPOI／OSMの役割分担

現状のOpenPOIは店舗・飲食・食品許可データ・鉄道駅が中心で、位置やカテゴリに限界がある。

公式OpenPOIの大まかなカテゴリは、restaurant, cafe, fast_food, bakery, grocery, convenience_store, retail_other, medical, education, station, public_facility, tourism 等。カテゴリ不明 unknown も存在。

**カテゴリが正規化されていない／間違っている施設は断定的に生活機能へ割り当てない。**「お酒の美術館」を美術館とする誤りなどに注意。データの営業終了、住所と座標不一致、市区町村矛盾を扱う。

優先ソース：
1. OpenPOI：食料品・コンビニ・飲食などの生活POI、駅。
2. OSM/Overpass：公園、図書館、薬局、公共施設のタグ補完。必要なら駅入口などの補助。
3. GSI：地図表示、地名、座標の確認。
4. 将来必要になった場合のみ他の公開施設データを追加。出典・ライセンス・都道府県差・保守コストを比較する。

**POI正規化モデル案：**
~~~
id, name, source, sourceId, lat, lon, normalizedCategory,
rawCategory, businessType, address, prefecture, city,
straightDistanceMeters, roadDistanceMeters?, 
routeProvider?, routeRetrievedAt?, 
licenses[], attributions[], retrievedAt,
confidence, coordinateAddressConflict, statusKnown?
~~~

同名でも別店舗のことがある。重複除去は名称だけでなく座標の近接とカテゴリーを考慮する。ライセンス・出典情報を捨てず保持する。POI精度の改良は既存v0.1.2のSTB-04〜07と同じデータ処理を**再利用**し、住環境機能のために二重実装しない。

### データ不足時の誠実な振る舞い

- API全滅：ポエムは地名のみで生成可能。住環境は「周辺施設データを取得できませんでした」と案内。
- 一部カテゴリのみ：確認できた施設だけを提示。空き欄を生成AI等で埋めない。
- 店名・座標が不自然：施設カードから除外または要確認にする。
- 最新の営業時間・休業：取得APIが保証しない限り表示しない。
- 年齢、収入、住民属性などデータなしの地域評判・治安を自動推定しない。

## 5. 情報設計：詩と生活の対比

現行アプリの生成ボタンは一つのまま。結果直後に「この地に住むと？」という二層目を置く。初版では先に既存THE EVIDENCEを整理し、**作品の創作根拠**と**生活POI検索の詳細**を分ける。

- Dream：物件名、ポエム本文、文体・濃度、架空の広告注記。
- Evidence：ポエムの主題に採用した施設や地理特徴の出典。
- Reality：生活用施設を目的別に検索した結果と距離、取得状態、地図。
- Related Projects：外部の類似ジェネレーターや関連研究への任意リンク。

「スーパーと公園が近い」ことは説明できても、「住みやすい」「治安が良い」「子育てに最適」は断定しない。生活の便利さは個人の条件で大きく変わるため、ランキングより比較可能な具体データを示す。

### さらに先のユニークな遊び

「ポエムを現実語に翻訳」：
~~~
DREAM：都市の煌めきを掌中に。
REALITY：周辺の駅・飲食店・スーパーが地図上で見つかりました。
根拠：名称、距離、API取得時刻
~~~
※上の言葉は**機能コンセプト例**で実際の地域についての主張ではない。

## 6. 実装分割

**最初の実装は生活圏画面すべてではなく、最小動作単位にする。**

| タスクID | 対象 | 依存 |
| --- | --- | --- |
| LIFE-00 | 5生活カテゴリのデータ要件・POIソース・未取得表示を決定 | STB-04/05の正規化方式 |
| LIFE-01 | 選択地点の確定と正規化済POIからの生活カード一覧 | STB-04/06 |
| LIFE-02 | 地図上の生活施設マーカーとカテゴリフィルター | LIFE-01 |
| LIFE-03 | 検索半径・施設件数・距離表示の改善 | LIFE-01/02 |
| LIFE-04 | Dream / Realityの行き来、説明・出典・読み込み状態 | LIFE-01/02 |
| LIFE-05 | ルーティング提供方式を別途調査（必要なら採用） | 実POI品質検証 |
| LIFE-06 | iPhone Safari・Android・デスクトップで操作試験 | LIFE-01〜04 |
| UI-REF-01 | フッターに関連作品のテキストリンクを追加 | [広告研究計画](ADVERTISEMENT_RESEARCH_PLAN.md) |

### 第一版の受入基準

1. 同じ座標についてDreamとRealityが一貫している。
2. 住環境表示で、必要なPOIが取得できたカテゴリのみ、施設名・直線距離・出典が表示される。
3. APIが落ちてもポエム生成機能は壊れない。
4. 直線距離に対して「徒歩○分」と誤表示しない。
5. 不確実性（未取得・不明なカテゴリ・古いデータ）が分かる。
6. 施設の分類誤りに対する回帰テストを含む。
7. モバイルの主操作を塞がず、視覚的な高級広告感を維持。
8. 選択地点変更時は古いRealityのデータが残らない。
9. 出典・ライセンスの表示と地域情報の外部送信に関する案内がある。

| 要件ID | 内容 | 背景 |
| --- | --- | --- |
| LIFE-D01 | THE REALITYが参照した選択座標・検索半径・取得日時・距離種別を明記 | 京都FLAG/CUBEでは同じ街区でも距離が異なる |

| LIFE-D03 | POIや公共計画に`existing / planned / announced / unknown`などの状態を導入。ただしOpenPOIのレコードに状態がない場合は安易に`existing`と確定させず、`unknown`とする | 識名の2028年度公共施設・2040年度LRT計画を現存施設に混ぜない |
| LIFE-D04 | 広域イメージ（県全体の自然・歴史）と、選択ピン周囲の現実の施設を分離 | 那覇松尾の沖縄リゾート主題と近隣徒歩圏は別の地理スケール |
| LIFE-D05 | 大型商業施設と食品スーパー・コンビニ、医療、教育、公園を用途別に表示 | 福岡・札幌の広告では生活目的ごとに距離と施設を示す |
| LIFE-D06 | 宣伝上の「便利」「安心」「快適」をそのまま事実として出力しない | 実広告の価値判断は独立した事実検証ではない |

### 施設の稼働状態の慎重な扱い

- APIで取得したことだけをもって「営業中・利用可能」とは断定しない。`status=unknown`を標準とし、`existing`は信頼できる十分新しい証拠があるときだけ。
- 予定施設は原則、**現在使える店舗・施設のランキングから除外**する。別の「計画中」タブを将来採用する場合も公的な出典・計画日・変更可能性を示す。
- 建物や店舗の出入り口が分からない場合、地図上の施設ポイントまでの直線距離と明示する。
- 路線計画は駅までの徒歩経路、列車所要時間、現在の交通網として扱わない。
- 調査で見つけた広告の施設名や距離を、任意地点のREALITY表示に流用しない。運用時には地点座標から改めて検索する。
