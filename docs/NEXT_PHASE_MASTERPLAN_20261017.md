## 0. ゴールと編集方針

利用者が地図から任意地点を選ぶと、周辺の実データから**通常の不動産広告なら強く評価される自然・公共・文化施設**と、**暗渠・側溝・郵便ポスト・マンホール・カーブミラーなどの小さすぎる都市設備**の両方を発見し、実在の架空高級レジデンス広告のように大真面目に美化する。店舗はラーメン屋一般、ピザ店、二郎系、確認済ブランド（ラーメン二郎・天下一品等）を誤混同せずに専用コピーを使う。

**広告として完結**させる。文章の下に「このポエムの着想源は暗渠」と種明かしせず、LOCATION HIGHLIGHTSを物件の周辺施設PRとして配置する。「○○暗渠 / 所在地 / 距離 / 確認できれば徒歩分数 / 専用見出し / PR文」。創作物件は実在と誤認させず、事実の出典と不明点をTHE EVIDENCEに分け、生活実用情報はTHE REALITYに分ける。施設・信仰・支援の利用者を笑いの対象にはせず、**高級広告の過剰な比喩**をユーモアにする。

非ローカル・軽量静的Web・GitHub Pagesを維持。公開APIを無制限の無料本番基盤とみなさない。コード完成、CI合格、Pages配信、実ブラウザ、スマートフォン実機を常に別々に記録する。

## 3. 改修で固定するデータ契約

取得層と表現層を混ぜず、以下の**概念フィールド**を段階導入する（既存STBレコードをいきなり一括変更しない）。

| レコード | 必須の観点 | 不明時 |
|---|---|---|
| SourcePOI | provider、providerId、OSM node/way/relation、raw tags、source timestamp、ライセンス、元座標/geometry | 出典や座標不明は主題候補にしない |
| PlaceIdentity | 公開データの施設名、確認済のブランド、上位業態、細分類、facility type evidence | 固有名なしのインフラは「側溝」「郵便ポスト」など**一般名称**に限定し、固有地名を捏造しない |
| SpatialEvidence | elementType、point/line/polygon、nearestSegmentPoint、distanceMeters、distanceMethod、geometryConfidence、searchRadiusMeters | 線の中心点が不適なら距離を保留し、近接を断定しない |
| AddressEvidence | facilityAddress、addressParts、addressSource、addressConfidence、geocodeDate、locationPrecision | 住所なしなら「所在地詳細：公開データ未収録」。選択地点の住所は移植しない |
| SubjectDecision | eligibility=allow/context_only/suppress/needs_review、safeAngles、forbiddenClaims、reasonCodes、matchedTag/brand | 未確定は専用コピーに昇格しない |
| WalkEvidence | routeProvider、pedestrianProfile、entryPoint、routeMeters、computedMinutes、accessChecked、routeRetrievedAt | 経路未検証・入口なしは**徒歩分数を出さない** |
| ThemePlan | mainEvidenceId、secondaryEvidenceIds、genreId、copyVariantId、locationCardIds、dataVersion、style、intensity | 地名のみの安全な創作へ |
| DataHealth | OpenPOI/OSM別：not_queried/success/empty/partial/timeout/blocked/error、lastFetched | 「地域に存在しない」と言わない |

**安全性の一貫性**：施設がsuppressならPOEM本文、LOCATION、THE EVIDENCEの創作根拠に出さない。生活情報THE REALITYの出し分けは別のポリシーで判断し、文芸選定関数を流用して生活施設を誤削除しない。施設の一般分類・場所・観光利用可否を、その場の創作から発明しない。

**施設住所と地理表現の規則**：丁目・町名は元POI自身の属性、またはそのPOIの座標に対して信頼できる住所API/行政界データから得られたときのみ表示。行政区域名しか確認できない場合は「○○区まで確認」と表す。線地物（暗渠・排水路等）の「所在地」は単一の住所で表しにくいので、「○○町付近（確認できた範囲）」等の正確性ラベルを用い、長い線全体が同じ町内とは断定しない。POI名が登録されていない場合は「暗渠（名称未登録）」とする。

## 4. 地理検索の基本アーキテクチャ

### 4.1 検索対象と優先順位（POI細分類を本気で活かす）

**Tier A：既存安定系** 公園、川、駅、図書館、学校、博物館、商業、飲食など。既存OpenPOI取得とOSMクエリを壊さない。

**Tier B：広告独自性が高い小型設備** 郵便ポスト (amenity=post_box)、マンホール (man_made=manhole＋詳細)、街頭鏡 (highway=traffic_mirror)、自販機 (amenity=vending_machine)、宅配ロッカー (amenity=parcel_locker)、街路設備箱 (man_made=street_cabinet)、ベンチ (amenity=bench) 等。

**Tier C：線地物・地表下の機能** ditch/drain、水路＋tunnel=culvert、緑道、橋、道路階段、自然の川。OSM wayの最近接線分とアクセス・表記を検査する。OSMのculvertは道路や鉄道の下を通る**短い水路区間**を含み、「古くからある地下河川」等とは断定できない。

**Tier D：飲食・ブランド** shop=*、amenity=restaurant/fast_food/cafe、cuisine=pizza/ramen等、brand=*、brand:wikidata=*、確認済みの提供元のbrand。type=restaurantの店名に「二郎」を含むだけでラーメン二郎と推定しない。「二郎系」と「ラーメン二郎」は別ジャンル。

**Tier E：宗教建築・文化景観** place_of_worship、building=shrine/temple/church等、historic/tourism/heritageの付帯属性を分離。神社・寺院・教会等を宗教の種類で不当に差別しない。建築・景観・観光・史跡の裏付けに応じて安全な角度を許可し、信仰者・教義を茶化さない。

### 4.2 API実装方針

1. APIへ投げる前に**目的・カテゴリの優先度・半径・上限・CORSと利用条件**を確認。まずフィクスチャで正規化・距離・表現を検証する。
2. タグ群をまとめた**少数の、半径の限定されたOverpass QL**を使用し、タイムアウト・最大件数・応答サイズに上限を設ける。公衆APIを高頻度に呼ばない。大型クエリ一発で全カテゴリを網羅しようとしない。
3. OSMのpointは座標、way/areaはgeometryの最近接地点を評価。詳細のgeometryが欠ける場合はunknown／low-confidenceとして表示しない、または追加取得を明示操作で限定実行。
4. **unnamed features**：正しく分類された公共設備だけ、OSM element IDを施設IDとして保ち「名称未登録の○○」という一般ラベルを採用する。住所・色・利用可・起源を付加しない。
5. 既存のOpenPOIとOSMを正規化して重複マージ。距離40m以内＋同名でも異業態やブランドが違えば安易に融合しない。施設が同じなら出典を複数残す。
6. 取得対象が500件出てもUIは全部表示しない。ソース結果の任意順による先頭12件をやめ、**検証→カテゴリ内で近さと明示属性を採点→多様性を確保→UI上限**という順序にする。
7. 再生成では、同じ座標・検索設定の新しいHTTP呼出しを不要にする。キャッシュキーは座標丸め＋検索半径＋カテゴリ群＋データ契約版＋取得日時。同一の施設データを文体別に順位付けする。時間経過や明示再検索のときに更新する。
8. status：not_queried / partial / failed / zero_resultを区別。API取得不可時も地名のみポエムは継続。**見つからない＝存在しない**とは書かない。
9. 長いクエリや429/CORS/5xxが起きたらバックオフ、部分結果を保持、再試行を無限ループしない。大量の「クエリ×ジャンル」は禁止。公開無料サーバーの規約・負荷・帰属を再点検する。

OSM参照： [Overpass QL](https://wiki.openstreetmap.org/wiki/Overpass_API/Overpass_QL)、[公開API利用条件](https://wiki.openstreetmap.org/wiki/Overpass_API)、[culvert](https://wiki.openstreetmap.org/wiki/Tag:tunnel%3Dculvert)、[drain](https://wiki.openstreetmap.org/wiki/Tag:waterway%3Ddrain)。**オープンなデモAPIはSLAも無制限利用保証もない**。

### 4.3 半径・「最も近い」の正確性

- POEM/LOCATION基本は既存850mを起点。半径拡張はジャンル単位で段階的に認可：日常商業は～1.5km、休息・銭湯等は～3km、文化・名所は～5kmを**検討上の上限候補**とする。利用者が望まない広域全件検索を自動起動しない。
- 比較する距離はpointならその座標、wayなら当該線分の最も近い点（少なくとも点中心値より妥当な値）。道の直線距離と歩行ルート距離は別フィールド。
- 網羅性の証拠がない「最寄り」断定は禁止。「今回取得できた範囲では近い」「取得範囲内で確認できた最短候補」と表す。
- 公園のpolygon中心点と入口は一致しない。入口情報がなければ徒歩分数の基点に使わない。

## 5. テーマ選定と文章生成の再設計

- 役割分担：**POEM**は格調高い架空広告のコンセプトコピー、**LOCATION HIGHLIGHTS**は実在施設・街の地物そのものを売り込む施設PR、**THE EVIDENCE**は取得根拠、**THE REALITY**は生活情報。
- SelectionPlanを導入：主役1件と補助0〜2件（必要時）を選び、id/根拠/安全な着眼点/コピーIDを固定。POEMの主役と広告カードの先頭を必ず一致させる。再生成は表現の変奏を優先し、主役変更は明示操作あるいは仕様上の選択方式を決めた後に実装。
- 採点要素は「出典・地理の信頼度」「ジャンルの固有性」「意外性」「自然・文化・教育等の良さ」「近さ」「直近使用頻度」を分離。単に駅を低く、側溝を高くするだけの強制ランキングにしない。候補が複数ある場合に主役が毎回同じになる偏りを監査する。
- 事実の文：取得ソースに明記された施設種、名称、住所、距離まで。詩の文：大胆な比喩は許すが、史実・信仰・ブランドメニュー・眺望・行政サービス・学区・営業状態を創作しない。
- LOCATION PRは**編集者視点の説明禁止**。「ご紹介します」「このポエム」「着想源」「広告らしい言葉へ昇華」等を本文に入れない。ブランド宣伝文句や公式コピーは転載しない。長い施設名にも自然に続く文章と重複回避を行う。
- POEM-01現行630短文の校閲は既存の[文言専用HANDOFF](handoff/POEM01_COPY_HANDOFF_20261017.md)に委譲済み。同じ辞書を別のコードPRで同時に編集しない。
- LOCATION-02：先に29細分類×3の質を磨き、採用頻度・実データの網羅性を見て重点ジャンルから10案に拡張。固定件数を達成するために不自然な言い換えを増やさない。優先例は暗渠、側溝、雨水桝、ポスト、カーブミラー、ピザ、ラーメン、ブランド、学校、公園、神社寺院等。

### 編集評価基準（各5点のルーブリックを後続で合意）

A. 高級レジデンスの広告としての完成度、B. 施設種別ならではの語彙、C. ポエムとPRの重複の少なさ、D. 日本語の自然さと余韻、E. 事実・倫理への適合。Eの不合格は他が高くても採用不可。高評価作例・低評価作例を同じfixtureに収めて回帰比較する。

## 6. 住所・直線距離・徒歩分数（ADDRESS-01 / WALK-01）

**現行仕様：直線 約○mのみ。徒歩時間は非表示。これは正しい安全措置であり、根拠がない数字を先に埋めない。**

- ADDRESS-01：まずPOI元データのaddress / OSM addr:* / verified行政区域名を優先。POI座標への地理院逆ジオコーディングなどを検討するが、クォータ・精度・行政境界/施設敷地と住所のずれをテストしてから。住所ソース・日付・粒度を持つ。
- WALK-01 Spike：pedestrian graphの候補はValhalla等の歩行者ルーティング。公開デモサーバーの安定利用・CORS・X-Client-Id・規約・レート制限を先に確認。費用・将来のセルフホスト/小規模バックエンドの可能性も比較して決定。公開デモを無条件の本番無料サービスにしない。
- WALK-01実装に必要な条件：(a)選択地点のアクセス可能な起点、(b)施設への公道上の到達地点または明示された入口、(c)歩行者経路の妥当性、(d)ネットワーク距離、(e)取得元・時刻・キャッシュ・失敗状態。
- 日本の不動産広告の距離表示は**道路距離80m当たり1分、端数切上げ**。経路距離が確認できたものだけ「徒歩約○分（経路の目安）」を出し、ルーティングAPIの予測所要時間と混同しない。 [首都圏不動産公正取引協議会](https://www.sfkoutori.or.jp/ippansoudanjirei/%E5%BE%92%E6%AD%A9%E6%89%80%E8%A6%81%E6%99%82%E9%96%93%E3%81%AB%E3%81%A4%E3%81%84%E3%81%A6/)。
- **暗渠・側溝・マンホール・線地物**は一般向け入口がないことがある。最寄り地点まで直線距離を表示できても、当該施設そのものへの徒歩時間は原則非表示。安全に観察できる公道上の地点が地理データから別に確認されたケースのみ条件付きで検討。
- 通れない私道、河川横断、立入禁止、学校構内、閉鎖された庭園への誤経路をテスト。0mも「徒歩0分」としない。取得不能で元の直線距離へ戻し、分数は隠す。
- [Valhalla公式ドキュメント](https://valhalla.github.io/valhalla/start/introduction/)では公開デモのfair use、外部アプリの申告、クライアント識別を求めている。採用決定前に最新条件を再確認する。

## 7. UI/UX と共有・アクセシビリティ（UI-01）

- 推奨順：**THE POEM → LOCATION HIGHLIGHTS → THE EVIDENCE → THE REALITY**（現行構成を基礎）。
- 先頭カードは主役、残り2枚は周辺紹介。施設種別ごとに同じ意匠は使うが、PRの特色は文章で出す。住所不明の余白で崩れない。
- 携帯幅320/375/390/428、タブレット、PCで実寸テスト。日本語の長い施設名、英数字混在住所、3カード/0カード/1カード、改行、読み上げ順序、contrast、focus表示、reduced motionを受入条件へ。
- 広告をコピーするときの範囲を別途明示。「ポエムだけ」「ポエム＋LOCATION広告一式」を独立操作にし、ユーザーがどこまでコピーしたか確かめられるようにする。公開現行はCOPY THE POEMでポエムのみ。
- 印刷/PDFは現行の印刷CSSではポエムとLOCATIONが複数ページにまたがる可能性がある。出力を「ポエム1ページ」「ロケーション付き広告2ページ」などのモードへ分けるか、少なくとも欠けがないことを先に確認。**出力検証なしに完成とはしない**。
- 初期表示の施設カードは生成まで未取得とし、古い選択地点の紹介を混ぜない。API遅延時にも旧地点の文章を出さない。

## 9. 検証マトリクスと指標

### テストを追加する順序

- 保護的除外漏れ、POI住所取り違え、徒歩分数捏造、誤ブランド断定、旧地点混入：**受入テスト上0件**。

## 10. 運用・ライセンス・費用と失敗からの復旧

- **リクエストポリシー**：1生成あたりのAPI呼出し数を記録。OSMの追加取得は必要時に限定。ユーザー操作なしに大量の外部検索を実行しない。可視外のTHE REALITY追加検索は原則遅延。
- **利用規約**：OpenPOI、OSM/Overpass、国土地理院、Leaflet、歩行者ルーティング候補を参照先ごとにURL/帰属/利用条件/キャッシュ許可/データ再配布の可否として管理。OSMの著作権表示とODbLを尊重する。
- **障害処理**：partial/blocked/timeout/empty/not_queriedを区別し、作品が出ない事態を増やさない。通常の地名だけの創作へ落とす場合はその旨を表示。データ不足で名所・店舗を補作しない。
- **プライバシー**：選択した位置や検索文字列を外部APIへ送ることを説明。APIキーや個人情報を公開Repo/クライアントへ入れない。
- **配信**：新しいsrcファイルを追加したら.github/workflows/deploy-pages.ymlのアーティファクトへのコピーも変更。PR CIがsrc/**とtests/**で起動することを確認。公開はmainマージだけで完成扱いにせずPages runとHTTP/画面で検証。
- **ロールバック**：対象PRの前の正常なcommit/Pages runを記録し、重大な誤分類・誤距離・データ過負荷があれば後続の該当PRをrevertする。既存POEM-01やLOCATION-01を丸ごと再実装しない。
- **ソース責任**：外部データは不完全。データ精度、コンテンツの倫理、API可用性、実機表示を別々に管理する。
